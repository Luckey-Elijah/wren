# Flutter release catalog and compatibility research

Checked 2026-10-26 against Flutter and Dart first-party sources. This note answers [Release catalog and compatibility](../issues/03-release-catalog-and-compatibility.md).

## Authoritative catalog

Flutter's [SDK archive](https://docs.flutter.dev/install/archive) covers stable, beta, and main downloads for Windows, macOS, and Linux. It describes each release by Flutter version, architecture, framework git ref, release date, and bundled Dart version. The machine-readable manifests are Flutter-hosted JSON at `https://storage.googleapis.com/flutter_infra_release/releases/releases_<os>.json`; the [Linux manifest](https://storage.googleapis.com/flutter_infra_release/releases/releases_linux.json) and [Windows manifest](https://storage.googleapis.com/flutter_infra_release/releases/releases_windows.json) were inspected directly. The corresponding macOS endpoint is `releases_macos.json`, though it could not be fetched through this research tool; validate it before implementing macOS support. [Flutter SDK archive](https://docs.flutter.dev/install/archive)

Each inspected JSON has `base_url`, `current_release` (channel → framework hash), and `releases[]`. A modern release entry supplies `hash` (framework git revision), `channel`, `version`, `dart_sdk_version`, `dart_sdk_arch`, `release_date`, `archive` (path relative to `base_url`), and `sha256` (complete SDK archive digest). `version` and `channel` are separate, so use both to identify a catalog entry; also include host OS and architecture for an actual downloadable artifact. The entry does **not** have an engine revision or a separate Dart artifact URL/checksum. [Linux release JSON](https://storage.googleapis.com/flutter_infra_release/releases/releases_linux.json), [Windows release JSON](https://storage.googleapis.com/flutter_infra_release/releases/releases_windows.json)

Follow-up checked 2026-10-27: not every historical entry has `dart_sdk_version` or `dart_sdk_arch`. The [Linux manifest](https://storage.googleapis.com/flutter_infra_release/releases/releases_linux.json) omits both for Flutter 1.22.6 stable and Flutter 2.2.0-10.1.pre beta, for example. [Historical release constraints](../issues/11-historical-release-constraints.md) excludes entries whose canonical bundled Dart version is missing or below stable 2.19.0 from Wren's first release.

The user's examples were present on 2026-10-26: Linux and Windows catalogs list stable `3.47.8` with Dart `3.13.7`, and beta `3.50.0-0.2.pre` with `dart_sdk_version` `3.14.0 (build 3.14.0-315.3.beta)`. This shows that beta Dart metadata is not always a bare semver string; avoid matching its first token alone without deciding what the runtime-reported version means. [Linux release JSON](https://storage.googleapis.com/flutter_infra_release/releases/releases_linux.json), [Windows release JSON](https://storage.googleapis.com/flutter_infra_release/releases/releases_windows.json)

For archive installation, join `base_url` and `archive`, verify `sha256`, then extract the platform bundle. That URL construction follows directly from the catalog fields. For Puro-style framework checkout, the catalog's `hash` identifies the git ref. A full archive and a framework checkout have different artifact/verification paths; the catalog checksum applies to the full archive only. [Linux release JSON](https://storage.googleapis.com/flutter_infra_release/releases/releases_linux.json)

## Engine and Dart artifacts

Flutter states that engine artifacts include the standalone Dart SDK and platform/build-mode engines. A released Flutter checkout's [`bin/internal/engine.version`](https://github.com/flutter/flutter/blob/master/docs/tool/Engine-artifacts.md) supplies the engine artifact revision; for example, the [file at the current stable framework ref](https://raw.githubusercontent.com/flutter/flutter/737ba8f885dc774b53b442759999a312c9461e4e/bin/internal/engine.version) contains `cf636b1dfb818dd6a3ff16e390e93b1a036969c8`. Thus framework `hash` and engine revision are distinct. Flutter's [cache source](https://github.com/flutter/flutter/blob/master/packages/flutter_tools/lib/src/cache.dart) builds engine artifact URLs under `.../flutter_infra_release/flutter/<engine-revision>/`, with artifact names selected for host/target. The release JSON does not supply a complete manifest or digest for these individual artifacts. [How Flutter fetches engine artifacts](https://github.com/flutter/flutter/blob/master/docs/tool/Engine-artifacts.md), [Flutter cache source](https://github.com/flutter/flutter/blob/master/packages/flutter_tools/lib/src/cache.dart)

Inference for Wren: the release catalog can drive `releases` and identify an install, but a shared-engine implementation must inspect the selected framework revision and follow Flutter's own artifact layout. The `sha256` in release JSON cannot verify an independently downloaded engine/Dart zip; Wren needs a separate integrity rule for that path. [Linux release JSON](https://storage.googleapis.com/flutter_infra_release/releases/releases_linux.json), [Flutter cache source](https://github.com/flutter/flutter/blob/master/packages/flutter_tools/lib/src/cache.dart)

## Constraint matching implications

`pubspec.yaml`'s `environment.sdk` is a **Dart** version constraint; `environment.flutter` is a Flutter version constraint. Flutter's pub integration currently enforces only the Flutter constraint's lower bound, even though its syntax can express a range. Wren must decide whether its own matching honors the complete written Flutter range or mirrors pub's lower-bound behavior. The selected Flutter release must be checked against its bundled Dart SDK version for `environment.sdk`. [Dart pubspec documentation](https://dart.dev/tools/pub/pubspec)

Dart uses the SDK constraint's lower bound as the package's default language version, so changing `environment.sdk` as a side effect of `wren set` can change language semantics. Prerelease versions sort below their eventual stable release, and packages needing a prerelease Dart SDK may need a prerelease SDK constraint. This makes beta matching and automatic beta selection a distinct policy decision. [Dart language versioning](https://dart.dev/language/versioning), [Dart publishing guidance](https://dart.dev/tools/pub/publishing)

## Gaps to decide before implementation

- Whether `releases` presents only artifacts installable on the current host or all OS/architecture entries. The inspected Linux and Windows catalogs expose x64 entries; check platform availability rather than assuming every version is universal. [Flutter SDK archive](https://docs.flutter.dev/install/archive), [Linux release JSON](https://storage.googleapis.com/flutter_infra_release/releases/releases_linux.json), [Windows release JSON](https://storage.googleapis.com/flutter_infra_release/releases/releases_windows.json)
- Whether beta candidates are eligible for automatic project selection when no explicit beta request exists. The catalog labels beta independently from version syntax. [Linux release JSON](https://storage.googleapis.com/flutter_infra_release/releases/releases_linux.json)
- How to validate individually downloaded engine/Dart artifacts if Wren does not install the checksummed full SDK archive. The catalog gives only the full archive SHA-256. [Linux release JSON](https://storage.googleapis.com/flutter_infra_release/releases/releases_linux.json), [Flutter cache source](https://github.com/flutter/flutter/blob/master/packages/flutter_tools/lib/src/cache.dart)
