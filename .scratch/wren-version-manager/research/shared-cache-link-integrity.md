# Shared cache integrity under Flutter writes

Research for [Shared cache integrity under Flutter writes](../issues/12-shared-cache-link-integrity.md), 2026-10-27. This is evidence and a design boundary, not a product decision. I compared Flutter 3.7.0 (near Wren's Dart 2.19 floor), a [recent released framework ref](https://raw.githubusercontent.com/flutter/flutter/737ba8f885dc774b53b442759999a312c9461e4e/bin/internal/engine.version), and current `master`. Only Linux host behavior was exercised locally; no full Flutter SDK was installed on this host.

## Finding

**A symlink from a release's `bin/cache/artifacts/engine` tree to a writable shared engine tree is unsafe.** `flutter precache --force` clears per-checkout stamps, then the engine updater extracts archives *into* `artifacts/engine/<platform-or-common>` and recursively changes modes there. The archive updater deletes only a child named after the archive, not the extraction directory itself. A symlink at `engine`, `common`, `linux-x64`, `darwin-x64`, or an analogous platform directory therefore routes writes into the shared target. Ordinary missing/mismatched stamps and an in-place framework/engine change can reach the same path. This mechanism is present in [3.7.0 `EngineCachedArtifact`](https://github.com/flutter/flutter/blob/3.7.0/packages/flutter_tools/lib/src/cache.dart#L843-L968), [3.7.0 archive updater](https://github.com/flutter/flutter/blob/3.7.0/packages/flutter_tools/lib/src/cache.dart#L1084-L1126), [recent released `EngineCachedArtifact`](https://github.com/flutter/flutter/blob/737ba8f885dc774b53b442759999a312c9461e4e/packages/flutter_tools/lib/src/cache.dart#L991-L1115), and [recent released archive updater](https://github.com/flutter/flutter/blob/737ba8f885dc774b53b442759999a312c9461e4e/packages/flutter_tools/lib/src/cache.dart#L1302-L1338). Both [3.7.0](https://github.com/flutter/flutter/blob/3.7.0/packages/flutter_tools/lib/src/commands/precache.dart#L132-L160) and [current `precache`](https://github.com/flutter/flutter/blob/master/packages/flutter_tools/lib/src/commands/precache.dart#L160-L196) expose `--force`.

Flutter's macOS extraction path is also a writer: on both [3.7.0](https://github.com/flutter/flutter/blob/3.7.0/packages/flutter_tools/lib/src/base/os.dart#L428-L461) and the [recent released ref](https://github.com/flutter/flutter/blob/737ba8f885dc774b53b442759999a312c9461e4e/packages/flutter_tools/lib/src/base/os.dart#L424-L462), it unzips to a temporary directory and, when `rsync` exists, runs `rsync --delete` into the requested destination; otherwise it unzips directly into that destination. On Linux, [Flutter invokes `unzip -o -q` into the requested directory](https://github.com/flutter/flutter/blob/737ba8f885dc774b53b442759999a312c9461e4e/packages/flutter_tools/lib/src/base/os.dart#L247-L263). Neither path isolates a symlinked destination.

The package set itself changed: [3.7.0 `FlutterSdk` lists only `sky_engine`](https://github.com/flutter/flutter/blob/3.7.0/packages/flutter_tools/lib/src/flutter_cache.dart#L227-L257), while the [recent released ref lists `sky_engine` and `flutter_gpu`](https://github.com/flutter/flutter/blob/737ba8f885dc774b53b442759999a312c9461e4e/packages/flutter_tools/lib/src/flutter_cache.dart#L253-L285). The web archive name and postprocessing also changed between those revisions, and current `master` stages Dart SDK extraction differently. Wren must derive its expected artifact inventory from each supported framework revision or use a tested per-revision family allowlist; one hard-coded modern cache layout would misclassify historical releases. The conservative private-copy boundary works across these sampled writer shapes, but full historical coverage still needs install/repair validation per supported release family. [3.7.0 web updater](https://github.com/flutter/flutter/blob/3.7.0/packages/flutter_tools/lib/src/flutter_cache.dart#L160-L225), [recent released web updater](https://github.com/flutter/flutter/blob/737ba8f885dc774b53b442759999a312c9461e4e/packages/flutter_tools/lib/src/flutter_cache.dart#L166-L192), [`master` Dart updater](https://github.com/flutter/flutter/blob/master/bin/internal/update_dart_sdk.sh#L137-L215).

## Targeted Linux experiment

I created two temporary release trees whose `artifacts/engine/linux-x64` entries pointed at one temporary shared directory. With `engine.bin=original` in the shared directory, `unzip -o -q artifacts.zip -d release-A/.../linux-x64` (the command shape Flutter uses) changed both the shared file and release B's view to `updated`. In a separate file-link variant, Linux `unzip -o` replaced a linked *file* with a private regular file and left its original target intact. A simulation of the 3.7.0 Dart updater's move/remove/unzip sequence changed only the checkout's `dart-sdk`, leaving the linked target `original`. These observations demonstrate the directory-link hazard and the tested shell detachment behavior. They do not prove macOS behavior, every archive layout, Flutter tool behavior end to end, or that an editor never writes through a linked SDK. Flutter's [Linux unzip command](https://github.com/flutter/flutter/blob/737ba8f885dc774b53b442759999a312c9461e4e/packages/flutter_tools/lib/src/base/os.dart#L247-L263), [macOS alternate extraction](https://github.com/flutter/flutter/blob/737ba8f885dc774b53b442759999a312c9461e4e/packages/flutter_tools/lib/src/base/os.dart#L424-L462), and [3.7.0 Dart replacement](https://github.com/flutter/flutter/blob/3.7.0/bin/internal/update_dart_sdk.sh#L128-L183) explain the tested operations.

## Layout and integrity checks implied by the evidence

**Proposed safe boundary, subject to the product choice:** Wren keeps an immutable, staged-and-validated engine/host artifact *source* keyed by engine commit and archive variant. Each checkout owns its writable `bin/cache` and `artifacts/engine` directories. It materializes engine and `pkg` files into that private tree with independent files: try a filesystem copy-on-write clone, otherwise copy bytes. A copy-on-write clone shares physical extents until a write while keeping changes private to the destination; Linux requires filesystem support and same-filesystem placement, while APFS supports file clones on the same volume. Do not use hardlinks, which share an inode and transmit in-place writes. Optional whole-entry links for `dart-sdk` and `flutter_web_sdk` use absolute targets inside a versioned Wren store; never link a cache parent. If Wren promises isolation even from arbitrary direct writes by an editor or user process, use independent files for these two entries too. [Linux reflink semantics](https://man7.org/linux/man-pages/man2/ioctl_ficlone.2.html), [Apple APFS clone behavior](https://developer.apple.com/documentation/foundation/about-apple-file-system), [Dart link deletion semantics](https://api.dart.dev/dart-io/Directory/delete.html).

- **Cheap readiness / prelaunch:** under Wren's release and shared-entry locks, confirm the recorded framework HEAD, tracked `engine.version`, store key and host/architecture, ready manifest, exact allowed link types/targets (`lstat` plus resolved path), non-dangling required links, private directory boundaries, private Flutter/Dart stamps matching the expected engine, and existence/executable mode of required host tools and representative files. Treat missing or redirected paths as “needs repair.” Flutter's own up-to-date check is weaker: it checks stamps and expected directory existence, not file hashes. Direct editor invocations through a printed SDK path bypass Wren's prelaunch check until a later Wren operation. [Flutter cache freshness checks](https://github.com/flutter/flutter/blob/737ba8f885dc774b53b442759999a312c9461e4e/packages/flutter_tools/lib/src/cache.dart#L930-L942), [engine directory checks](https://github.com/flutter/flutter/blob/737ba8f885dc774b53b442759999a312c9461e4e/packages/flutter_tools/lib/src/cache.dart#L1014-L1039), [Wren external-use decision](../issues/09-external-sdk-integration.md).
- **Full `repair`:** walk the expected artifact manifest; verify every shared source file and private materialization against Wren-recorded hashes, sizes and types, and verify link targets and permissions; compare engine stamps and bundled Dart version; run the required Dart/host-tool smoke checks after staging; reconstruct any damaged private tree from a verified shared source, or re-fetch and validate a damaged shared source before publishing a new generation. Do not silently “repair” a shared target in place while other releases or external SDK users can still access it. The release catalog's archive SHA-256 is for the *whole Flutter SDK archive*, not individual engine ZIPs; Wren can use the provider transfer checksum and then record its own extracted-file manifest for later local integrity detection. [Flutter artifact MD5 transfer check](https://github.com/flutter/flutter/blob/737ba8f885dc774b53b442759999a312c9461e4e/packages/flutter_tools/lib/src/cache.dart#L1346-L1410), [Wren catalog evidence](release-catalog.md), [Wren repair decision](../issues/08-recovery-and-lifecycle.md).

The unresolved product tradeoff is **how much disk saving justifies the complexity and limits of live links**. Directly linked engine directories give strong savings but can corrupt multiple releases during a normal Flutter update. Independent private engine files preserve transparent Flutter and editor behavior; on APFS and reflink-capable Linux filesystems they can still share physical extents, while on other filesystems they cost roughly one extracted copy per release. Wren could keep only the linked Dart/web entries with the documented direct-write caveat, or choose copies for an unconditional isolation promise. A cross-platform overlay/sandbox could regain more sharing but would add substantial platform-specific behavior to direct SDK paths. [Linux clone and fallback constraints](https://man7.org/linux/man-pages/man2/ioctl_ficlone.2.html), [Apple APFS cloning](https://developer.apple.com/documentation/foundation/about-apple-file-system), [Wren direct SDK-path commitment](../issues/09-external-sdk-integration.md).
