## Question

What stable SDK paths or shims should Wren expose to editors, CI, and shell workflows, and how should those consumers choose a release? In particular, can they invoke a managed Flutter/Dart executable directly, and if so how does Wren keep direct use safe when `remove` can reclaim a checkout or shared engine cache without a Wren-held process lease?

## Answer

`wren setup` creates opt-in `flutter` and `dart` launchers in a dedicated shim directory and prints the one-time PATH and editor configuration steps. It does not edit shell startup or editor settings. The shims select a release exactly as `wren flutter` and `wren dart` do, forward SDK arguments unchanged, and hold Wren's process lease until the SDK process exits.

For CI or a deliberate one-command override, `WREN_FLUTTER_RELEASE=<release>` selects that exact installed Flutter release for a shim or Wren SDK launch. `wren --release <release> flutter ...` and `wren --release <release> dart ...` provide the same override when invoking Wren explicitly; the CLI option wins over the environment variable. Wren parses `--release` before the SDK command name and never consumes arguments after `flutter` or `dart`. Exact selection takes precedence over project constraints and the global fallback. A missing or unusable exact release fails without fallback and points to `install` or `repair`; an installed release that conflicts with the project's pubspec is launched, leaving incompatibility errors to Flutter/Dart with no separate Wren mismatch warning.

`wren sdk-path [<release>]` prints only the real Flutter SDK root of one installed release. Without an argument, it resolves the active release for the current directory, including an exact environment override; with an argument, it returns that release's fixed path. It fails rather than print a missing or unusable path. Every successful call records that release as externally used. The path never retargets to another release. Direct execution of Flutter or bundled Dart through a Wren-supplied SDK path is supported; a manually discovered internal checkout path has no direct-use guarantee.

VS Code can be configured once to call `wren sdk-path` through `dart.getFlutterSdkCommand`. It chooses a release when the editor discovers the SDK for a workspace; a changed selection requires an editor reload. The setup instructions explain that the command normally runs from the workspace folder and that multi-root workspaces may need an explicit working directory. JetBrains editors use the fixed path printed for a release in each project's Flutter SDK setting; switching releases requires changing that setting. Editors may launch the bundled Dart executable directly, so Wren cannot treat them as Wren-launched SDK processes or infer when they close.

The external-use record persists without any protect/unprotect step. If `remove` or `repair` would change a recorded release checkout or its release-private cache, Wren asks the user to close affected editors and confirm before proceeding. Rebuilding only the retained shared artifact source does not change an editor's live SDK path and needs no editor-close confirmation. Decline or unavailable confirmation for a private-file change returns status `6`; an unrelated release can still be removed when it leaves recorded assets intact. Successful repair keeps the record for later editor use; successful removal clears it. Wren-launched process leases still make destructive operations wait for those processes under [Recovery and lifecycle](08-recovery-and-lifecycle.md). Confirmation is the user's assertion that direct external users have stopped; Wren does not claim to detect those processes.

`flutter upgrade` and `flutter channel` remain transparently forwarded, but changing a Wren-managed release in place is unsupported; install another release through Wren instead. Wren checks for changed framework identity or cache integrity when it next validates the release, marks detected damage as needing repair, and follows the existing repair contract. [Shared artifact reuse policy](13-shared-artifact-reuse-policy.md) requires private live artifact files, so Flutter's cache writes through an exposed SDK path cannot mutate another release or Wren's retained shared source.

## Comments

First-round decisions (2026-10-27): support editors that require a Flutter SDK directory in the first release; offer opt-in `flutter`/`dart` PATH shims alongside explicit Wren commands; and provide CI an exact Flutter-release selector independent of the set of compatible releases currently installed. Path lifetime and selector mechanics remain open.

Second-round decisions (2026-10-27): editor SDK paths are fixed to one installed Flutter release, with no moving "current" path. Exact selection is available through `WREN_FLUTTER_RELEASE=<release>` for shims and Wren commands and through `wren --release <release> flutter ...` or `wren --release <release> dart ...`; the CLI option wins when both are set. An exact selection bypasses project constraint matching and launches the chosen installed SDK, leaving any project incompatibility for Flutter/Dart to report. The human's wording suggests no separate Wren mismatch diagnostic; confirm in the consolidated answer.

Third-round decisions (2026-10-27): supported direct editor use requires persistent protection for the release-specific SDK path. Protection prevents `remove` and affected repairs from changing its checkout or shared assets until that protection ends; internal checkout paths not provided for editor use have no direct-use guarantee. Wren provides an opt-in setup command that creates `flutter`/`dart` launchers in a dedicated shim directory and prints PATH instructions without editing shell startup files. How Wren registers and ends protection remains open.

The proposed `wren expose` and `wren unexpose` command names were introduced by the agent, not requested or decided by the human. That command proposal is withdrawn. The remaining questions are how Wren registers and ends persistent protection, whether operations blocked by it fail or wait, and how to handle upstream SDK commands that mutate a managed checkout.

UX constraint from the human: setup should be intuitive and mostly one-time; routine SDK and editor use should not require manual protection bookkeeping. Reassess persistent protection behind that user experience before choosing any command surface.

Editor capability check: [Dart Code's SDK lookup implementation](https://raw.githubusercontent.com/Dart-Code/Dart-Code/master/src/extension/sdk/utils.ts) can run a path-printing command from a single workspace folder during SDK discovery, but offers no matching close callback; a running editor does not automatically adopt a newly selected SDK. [Flutter's JetBrains plugin](https://github.com/flutter/flutter-intellij) uses a configured SDK root path; no equivalent command-based resolver was found in its inspected settings code. A one-time VS Code lookup setting and a fixed per-project JetBrains path are plausible first-release flows, with a restart or manual path change needed when the editor should switch releases. The previous `expose`/`unexpose` command question is superseded by a simpler UX exploration.

Revised-round decisions (2026-10-27): when Wren supplies a release-specific SDK path, it remembers that release as externally used. Routine use needs no manual protect/unprotect step. An affected `remove` or `repair` asks the user to close editors and confirm before changing protected files; noninteractive use fails with an explanation. VS Code uses a one-time path-lookup setting that chooses the active release when its workspace opens, while JetBrains uses a fixed path per project and needs a setting change to switch releases. Wren preserves transparent argument forwarding for `flutter upgrade` and `flutter channel`; using them to mutate a managed release is unsupported, and Wren detects changed checkout/cache state and requires repair. The command interface for the path lookup remains to be decided.

Final interface decision (2026-10-27): add one `wren sdk-path [<release>]` command. With no argument it selects from the current directory; with a release it returns that fixed release's SDK root. It prints only the path and automatically records external use. `wren setup` prints one-time VS Code and JetBrains configuration steps. No separate protect/unprotect command is part of the decision.

The human confirmed the consolidated answer on 2026-10-27. The answer above is the resolution.

Further technical finding: Flutter's [bootstrap](https://raw.githubusercontent.com/flutter/flutter/master/bin/internal/shared.sh) can update checkout cache state during ordinary launches; [`flutter channel`](https://raw.githubusercontent.com/flutter/flutter/master/packages/flutter_tools/lib/src/commands/channel.dart) can move the Git checkout, and [`flutter upgrade`](https://raw.githubusercontent.com/flutter/flutter/master/packages/flutter_tools/lib/src/commands/upgrade.dart) can reset it. Flutter's [Dart updater](https://raw.githubusercontent.com/flutter/flutter/master/bin/internal/update_dart_sdk.sh) and [artifact cache updater](https://raw.githubusercontent.com/flutter/flutter/master/packages/flutter_tools/lib/src/cache.dart) can replace cache paths. A Wren lease or persistent exposure prevents Wren from reclaiming files during use, but does not itself prevent the upstream SDK from changing a linked shared cache entry. The link layout and validation rules must preserve shared-entry integrity under these upstream writes.

Technical context: [Dart Code SDK discovery](https://dartcode.org/docs/sdk-locating/) uses the Flutter SDK root and its bundled Dart SDK; its [settings](https://dartcode.org/docs/settings/) accept an SDK path or a command that prints one. Flutter's [bootstrap script](https://github.com/flutter/flutter/blob/master/bin/internal/shared.sh) writes to `bin/cache` and holds a startup/update lock, not a lifetime lease for editor processes. A direct SDK path lets an editor invoke the bundled Dart analyzer outside Wren's process lease. A wrapper for only `bin/flutter` and `bin/dart` would not cover all those processes. Any supported direct path therefore needs a persistent protection rule or an independently managed copy.

The live shared-link concern in the historical technical comments is resolved by [Shared artifact reuse policy](13-shared-artifact-reuse-policy.md). The answer above now distinguishes editor-visible private files from the retained shared source.
