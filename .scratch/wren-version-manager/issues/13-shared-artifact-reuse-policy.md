## Question

Given [Shared cache integrity under Flutter writes](12-shared-cache-link-integrity.md), what cache-reuse boundary should Wren promise for its first release? Decide whether every artifact visible through an exposed SDK path needs independent per-release files (copy-on-write clones where supported, byte copies otherwise), or whether whole `dart-sdk` and `flutter_web_sdk` links may remain with a narrower guarantee about direct writes. State the accepted disk-use and compatibility tradeoff, and update the earlier shared-cache and repair decisions accordingly. Preserve transparent `flutter`/`dart` forwarding and supported direct editor use.

## Answer

Every live engine, bundled Dart, web, and package artifact reachable through an installed release's SDK path is **release-private**. Wren keeps a validated, immutable shared engine cache as a source keyed by engine revision and host/archive variant. When preparing an artifact from that source, it tries a filesystem copy-on-write clone and falls back to copying bytes. It never symlinks or hardlinks a live SDK artifact to the shared source. The checkout's stamps, snapshots, downloads, and other mutable Flutter state also remain private. On filesystems without cloning, Wren accepts the disk cost of one retained source plus an extracted copy for each release. This preserves transparent Flutter command forwarding and direct editor use without allowing a write in one release to change another release's live files. [Shared cache integrity under Flutter writes](12-shared-cache-link-integrity.md) supplies the source and experiment behind this boundary.

Wren retains each validated shared source while an installed release references its engine/host/archive key, and reclaims it after the last dependent release is removed, subject to active install or repair work. Installs sharing that key still join one source download and can prepare their private files from it. Device and build-target artifacts that Flutter fetches on first use stay private; Wren does not automatically promote them into a shared source in the first version. Artifacts Wren itself downloads and validates for install or repair may be reused as sources.

The retained source's integrity is a **release-readiness requirement** even though live files are independent. Once Wren detects source damage, it marks every dependent installed release as needing repair, including releases with healthy private files. Cheap `list` and prelaunch checks inspect recorded identities, source readiness metadata, required file presence, private cache boundaries, and stamps; they do not hash every file. Full `repair` validates the source and release-private files, including optional device/build-target artifacts already present, without fetching never-used platforms. Repair stages a source replacement once, validates each dependent release, and automatically clears “needs repair” for those whose private files are sound. It repairs damaged private files for the affected release. A source-only replacement changes no live SDK path and needs no editor-close confirmation; a private-file repair still obeys Wren-launched process leases and the external-use confirmation rule in [External SDK integration](09-external-sdk-integration.md). Direct editor calls through a printed SDK path can bypass Wren's prelaunch check, so a Wren needs-repair state cannot stop an already running editor from using healthy private files.

This supersedes the live shared-artifact linkage and runtime shared-artifact lease assumptions in [Install and cache model](05-install-and-cache-model.md). It keeps the source integrity consequence from [Recovery and lifecycle](08-recovery-and-lifecycle.md) while changing repair and removal to distinguish the retained source from release-private live files. The method for inventorying and validating first-use optional artifacts across supported Flutter releases is the next investigation in [Optional artifact repair inventory](14-optional-artifact-repair-inventory.md).

## Comments

First-round decision (2026-10-27): Wren promises release isolation for every artifact reachable through a supplied SDK path. Engine, bundled Dart, web, and package artifacts have independent per-release files: use filesystem copy-on-write clones when supported and byte copies otherwise. A live SDK path must not link or hardlink to the shared artifact source, so Flutter and direct editor writes stay local to that release.

Second-round decision (2026-10-27): Retain one validated immutable source per engine revision and host/archive variant while at least one installed release uses it. Use that source to prepare later releases and to repair private materializations without redownloading when healthy; reclaim it after the last dependent release is removed under the existing lifecycle rules. On filesystems without cloning, accept the extra extracted copy per engine.

Third-round decisions (2026-10-28): Device and build-target artifacts that Flutter fetches on first use stay private to that release; Wren does not automatically promote those downloads into a shared source in the first version. If Wren detects damage in a retained shared source, every installed release depending on that source is marked as needing repair, even when its private files are healthy. This makes source integrity a release-readiness requirement despite physical separation of live files.

Fourth-round decision (2026-10-28): Rebuilding a damaged shared source through repair automatically clears “needs repair” for every dependent release whose private files also validate. A release with damaged private files remains in need of its own repair. Rebuilding only the source changes no live SDK path, so it does not require an editor-close confirmation; the existing confirmation still applies when a repair changes a recorded release's private files.

Fifth-round decision (2026-10-28): Full `wren repair <release>` validates and restores optional device or build-target artifacts already present in that release's cache. It does not fetch artifacts for platforms never used by that release. These first-use artifacts remain private, and a damaged present artifact may require a large redownload.

The human confirmed the consolidated answer on 2026-10-28. The answer above is the resolution.
